# Bounded client inventory follow-up

An actual camera preflight stopped when the compositor changed descriptors
during all three local thread attempts. No originals were committed, no camera
configuration or capture began, and root/dark closure plus a new full idle
check were independently confirmed. The failed result remains unchanged.

The reader now raises SnapshotChanged for exhausted local thread inventory
changes so the existing bounded whole-scan retry handles them. Both full passes
must be repeated. The same four-second and500000-metadata budget is shared;
observed camera access is sticky across discarded work. The existing outer
three-read/eight-second contract also recognizes this typed transient reason
and the already reviewed numeric-proc-stat task-exit reason. Permission,
identity reuse, camera mappings, metadata limits and unknown errors still stop.
No process is killed, excluded or whitelisted. A later complete check is
mandatory; an incomplete inventory is never converted into an empty one.

The source retains example host/path bindings and refuses direct use on a
non-matching installation. It is source for review, not an installed privilege
grant. Never replace the live reader with an unbound example. The isolated VM
passed79 reader and28 helper tests;26 presence/order/direction tests and a
real root-to-user one-use claim/reuse-rejection integration also passed.
The sanitized source passed the same79 reader tests locally. No camera
start, pixels, biometric decision or privilege grant is part of these tests.

The newly staged actual reader completed two new left/right30RGB+30IR
capture cycles with complete teardown, exact restoration and external idle
verification. Twenty passive normal-desktop observations also passed in
roughly0.9seconds each, all on the first outer read. No artificial compositor
load was generated. This is a bounded functional check, not a long-duration
reliability study. Standalone project source remains GPL-3.0-only.
